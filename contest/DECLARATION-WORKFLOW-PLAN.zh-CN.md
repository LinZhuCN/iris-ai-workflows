# Declaration-to-monitoring demo: design and development plan

[English](./DECLARATION-WORKFLOW-PLAN.md) | [简体中文](./DECLARATION-WORKFLOW-PLAN.zh-CN.md)

## Goal and acceptance boundary

用户创建一份新的数据使用声明。AI Hub Agent 根据 HIPAA 来源评估拟议用途，解释风险或重要缺失输入，并在人工决策前支持修订。获批且可执行的声明随后可以驱动合成 IRIS 工作流。发送后自动监控会将实际用途与该确切获批声明进行比较。

UI 只需一次性说明应用是合成数据演示。普通结果使用直接表述：“未发现 HIPAA 合规风险”“发现 HIPAA 合规风险”或“需要补充信息”。结果应酌情描述提交的提案或观察到的批次。技术故障与业务结论分开呈现。

本计划取代了将两条固定成功路由视为面向用户工作流已完成的做法。现有投递和监控结果仍是有用基线。编写本计划不授权额外推理、发送、重置或部署更改。

## 1. User journey

1. 创建并保存声明草稿。
2. 提交不可变修订版本，以进入自动排队的 AI 审核。提交前显示模型额度；普通导航绝不触发推理。
3. 检查评估、针对具体问题的推理、来源摘录以及重要信息请求。
4. 将退回的提案编辑为新修订版本并再次提交。在该声明历史中保留之前的修订和评估。
5. 审核者针对确切的已审核修订版本予以批准、退回修改或拒绝。AI 的正面评估本身不是人工批准。
6. 对获批且受支持的配方，从页面显式运行合成批次。无需切换全局活动路由指针。
7. 观察器自动捕获批次，并根据声明和批准审核实际行为。显示关联结果和事件。
8. 记录事件审核和处置，不得悄然更改批准、重放批次或触发另一次模型调用。

预设聚合仍是上游基线。新的利用声明是主要交互工作流；用户不必重置演示或修改源代码来创建新声明。

## 2. Declaration model

在演示具有真实登记能力的地方使用受控选择项，同时允许自由文本业务说明，而不是固定的已批准用途段落。

| 分组 | 输入 |
|---|---|
| 身份 | 声明 ID/标题、修订版本、责任办公室、提交者 |
| 业务用途 | 预期用途/类别、具体活动、预期输出以及每个请求数据组的必要性 |
| 相关方 | 请求团队、接收方选择、合成接收方目录中的内部/外部关系 |
| 数据 | 请求的资源/字段选择、队列和记录数上限 |
| 处理 | 可识别性/去标识化主张、处理配方、预期访问、保留和后续共享 |
| 适用安排 | 相关时：声明的授权、协议或其他支持安排；不是普遍适用的强制清单 |
| 有效性 | 请求的起始和结束时间 |

将声明的接收方与传输/服务身份分开持久化。已登记组织事实、用户陈述、拟议处理和实际观察应具有不同来源属性。

初期可执行支持保持有限：现有四资源队列、明确允许的投影字段/转换清单，以及已登记的内部 SQL 接收方。可评估已编入目录的模拟外部用途，而不必建立外部连接。“可评估”和“可运行”是不同属性。必须明确显示不受支持的执行；不得悄然替换为内部质量改进配方。

## 3. Two review modes, one reusable evidence engine

### Declaration review: before approval or delivery

- 输入：不可变声明、已登记的合成组织/接收方事实、拟议数据配方和政策版本。
- 陈述可作为用户拟议内容的证据，但不能证明相应行为已经发生。不过，仍可根据这些明确陈述的前提评估提案。
- 不要要求先有已批准场景、收据或已验证投递才能评估拟议用途。不要仅因为用户提供的前提属于声明，就把所有前提标为“未解决”。
- 复用两阶段方法：识别相关问题，在服务器端检索来源上下文，再由 AI Hub Agent 判断这些问题。
- 即使没有观察到批次，矛盾的提案也可能构成风险。仅当某个具体缺失答案会改变评估时才请求补充信息；不要要求每位申请人都提供 BAA/DUA/患者授权。
- 返回问题状态、解释、所引用的声明字段、法律引用和重要问题。使用提案专用依据规则，而不是现有的仅限观察数据验证器。

### Observed-use review: after delivery

- 输入：确切的声明/审核/批准 ID 和哈希、当前已登记政策事实、冻结的来源/输出/配置以及实际收据。
- 复用现有完整性检查以及实际消息/会话关联。
- 将实际接收方、字段、转换和用途上下文与获批提案比较。获批并不会自动使不一致的业务用途变得合理。
- 使技术完整性故障与 AI 风险发现保持可区分。
- 不得拦截或撤销已完成的发送。发送前的确定性约束仍由 IRIS 强制执行。

两种模式都记录 Agent/模型、提示契约、知识索引/来源版本、SDK 会话、token 用量、尝试次数和时间戳。来源引用必须能解析到物化段落；不得捏造引用。

## 4. State, decision and message contracts

保持各状态维度相互独立，不要用一个状态字段承载所有含义：

- 修订版本：不可变的已提交快照；编辑会创建下一修订版本。
- 审核任务：queued / running / completed / failed / blocked_budget。
- 评估：no_risk_identified / risk_identified / information_required。失败任务没有评估。
- 人工决定：pending / approved / returned / rejected。
- 执行就绪状态：supported / unsupported / expired / superseded。
- 批次和监控：复用独立的投递、审核和事件状态。

只允许批准针对确切修订版本完成的评估，且要求当前所需政策/配置和有效时间范围。要求在新审核的修订版本中解决未解决风险/问题；首个实现不添加覆盖路径。退回/拒绝时记录原因。新修订版本不得继承评估、批准或执行权。一旦提交替代修订版本，就阻止执行较旧的获批版本；历史批次证据仍引用原修订版本。

在实现 BS/BP/BO 更改前，先设计以下逻辑契约：

- 审核请求：声明 ID、修订/摘要、审核模式、政策/索引/提示固定版本、任务/幂等 ID 和成本授权 ID。
- 审核结果：匹配的任务/修订身份、任务结果、完成时的评估、问题/疑问/引用和 SDK 来源信息。
- 批次命令：确切的获批修订/摘要、受支持的配方/配置哈希、唯一批次 ID 和执行授权。

为新的审核路径使用真实的 `Ens.Request`/`Ens.Response` 消息和 IRIS BP，并采用排队异步执行；浏览器不等待提供方响应。选定物理类签名之前，检查现有消息/超类 API。兼容时复用现有编排；MCP 仅作开发工具，不能作为运行时 Agent。

## 5. Cost, concurrency and execution controls

- 将固定的两批额度替换为每任务原子预留，且必须处于明确授权的有界演示预算内。
- 分别显示声明审核和发送后审核成本。没有足够授权时，提交不得消耗提供方请求。
- 保留两阶段请求上限、不自动重试、去重和显式故障报告。人工授权的重试是一个新的关联任务。
- 重复点击/轮询不得创建重复推理、批准或投递。并发修订/批准检查必须由服务器执行。
- 未来发送后审核额度可针对确切获批修订和新批次身份预留，并在捕获时绑定到实际收据。
- 没有模型额度时仍继续收集证据，但显示 blocked_budget，而不是复用其他声明的评估。
- 声明中不得接受任意 URL、凭据、可执行表达式、SQL 或 Production 编辑。

| `RiskReviewV4` 和分阶段检索 | 复用检索/引用机制；引入独立提案审核契约，而不是削弱观察验证 |

不要自动回填旧报告并将其视为成功的声明审核。旧基线记录在通过新路径显式审核前，仍须清楚标为旧版。安装/更新行为必须明确且幂等。

## 7. Development sequence and acceptance gates

| 阶段 | 交付物 | 必需验收 |
|---|---|---|
| D1：契约和持久化 | 声明/接收方/配方架构；修订和任务状态；审核/决定绑定 | 新的非模板提案已持久化；报告无效范围；编辑不能复用审核/批准；不调用模型 |
| D2：提案审核 | IRIS 请求/BP/结果路径、提案事实、检索、验证器、逐任务预算 | 正面、有风险和信息不全的提案夹具产生可区分的有效结果；真实故障仍为故障；重复提交只预留一次 |
| D3：交互审核和批准 | 表单、排队进度、证据、修订、退回/拒绝/批准 | 从浏览器创建新声明、检查结果、修订并决策；拒绝过期/失败/未审核的批准 |
| D4：获批执行绑定 | 对受支持配方提供显式批次操作；获批投影和收据关联 | 新获批声明无需重置或修改全局指针即可驱动自己的真实 BS/BP/BO 批次；不受支持/未批准/过期提案不得发送 |
| D5：发送后自动比较 | 通用批次发现/授权、确切批准关联、事件详情/操作 | 新批次无需手动启动审核即可被发现；实际证据关联同一修订；没有重复发送或审核 |
| D6：端到端验收和文档 | 真实浏览器演示流程、真实 Agent 检查和回归测试 | 正常、风险和缺失输入提交均可工作；修正/批准/发送/监控链路完成；token 统计与授权尝试相符 |

依赖关系：D2 依赖 D1；D3 依赖 D1/D2；D4 依赖 D3 的审核/批准契约；D5 依赖 D4；D6 依赖此前所有阶段。每个阶段都要更新直接相关的文档和测试，不要拖到最后才更新。

先进行免费测试，再单独授权真实推理：

1. 有合理且有界数据集的内部质量改进提案。
2. 在声明场景中未确立适用许可的外部营销可识别数据传输提案。
3. 缺少会影响决策的用途或接收方关系的模糊二次用途提案。
4. 修正后的修订版本；旧审核/批准无法授权该版本。
5. 获批的真实合成批次和发送后自动比较。
6. 接收方/字段/配置不匹配的受控漂移夹具；绝不为了展示风险而发送范围外数据。

真实模型验收应使用实际 Agent 输出，而不是预先确定的状态标签。运行前冻结案例预期；将技术拒绝与评估质量分别统计。免费验证后授权有限调用上限；不得复用已消耗额度。

## Completion definition

仅当用户可以通过 UI 创建新声明、获得其专属 AI Hub 评估、修订并取得人工决定、运行获批且受支持的合成批次，并检查自动关联的发送后审核时，工作流才算完成。仅有两个预配置的成功批次不满足此定义。竞赛打包、远程系统和任意流水线生成不在本开发计划范围内。

## D1 implementation and local verification

D1 已在 [DeclarationCatalog](./src/DeclarationCatalog.cls) 和 [DeclarationService](./src/DeclarationService.cls) 中实现，并在 [KnowledgeAPI](./src/KnowledgeAPI.cls) 中提供经过身份验证的路由。旧路由注册表及其业务批准保持不变。

### Contract and API

提案存储标题/所有者、用途类别/文本/活动/输出、接收方选择、资源/字段/队列/数量/必要性、处理配方/可识别性/访问/保留/后续共享、安排状态/详情以及 IRIS UTC 有效期整数边界（自 1840-12-31 起的秒数）。具体 JSON 示例见 [declaration_test.py](./declaration_test.py)。

已登记的组织和接收方事实单独捕获在 `context` 中，并固定到目录版本和哈希。选择项目不会授予已批准用途场景或 AI 评估。

| 方法 | `/api/monitor/v1` 下的 API 路径 | 契约 |
|---|---|---|
| GET | `/declarations/catalog` | 有界的合成组织、接收方、用途、数据和配方选项 |
| GET | `/declarations?after=...` | 最多 25 个最新声明修订；稳定的声明 ID 游标 |
| GET | `/declarations/:record_id` | 确切的不可变修订、关联任务/决定和执行就绪状态 |
| GET | `/declarations/:declaration_id/history?before=...` | 最多 25 个修订，按时间从新到旧；`older_before_revision` 用于继续查看历史 |
| POST | `/declarations` | `declaration_id`、`expected_revision`、`expected_digest`、`proposal` |
| POST | `/declarations/submit` | `record_id`、`digest`；幂等地创建审核意图 |
| POST | `/declarations/decide` | `record_id`、`digest`、`task_id`、`task_hash`、`action`、`reason` |

`expected_revision=0` 且父摘要为空时会创建修订 1。后续保存必须提供当前修订及其摘要；保存将创建新的不可变草稿。完全相同的丢失响应重试会返回已有修订，而不是创建另一个修订。提交操作只接受最新版本。提交替代版本后，较早批准会对未来使用标记为已被取代，但历史证据不会删除。

D1 创建一个 `blocked_budget` 任务，其中**预留/尝试请求数均为零**，评估和结果均为空。不会调用工作进程或提供方。已完成审核和决定绑定通过明确标记、事务回滚的框架夹具测试，而非插入为演示评估。不存在公开的完成/结果上传端点。

批准要求确切的当前已完成无风险任务、匹配的任务哈希、当前目录和有效时间范围。失败、有风险、未回答或未审核的提案不能批准。退回/拒绝决定要求任务已终结并提供原因；决定不可变。D2 必须先提供真实且经过验证的结果，正常应用才能批准新提案。

执行能力与执行就绪状态是分开的。现有七字段内部配方会被识别，但即使已批准的声明，在 D4 前也仍保持 `not_connected`。外部或不受支持的配方仍可评估，并带有 `capability.state=unsupported`；D1 不发送数据。

python3 contest/declaration_test.py --install
python3 contest/declaration_test.py --check

# 可选：显式创建一个新草稿；选择未使用的声明 ID。

自有本地安装现在包含三个持久化声明：

- `demo-declaration-quality`：修订 1 已提交为零预算审核意图；没有评估或决定。
- `demo-declaration-marketing`：修订 1 外部用途草稿；未执行。
- `demo-declaration-incomplete`：修订 1 和 2；修订 2 是当前草稿；未继承审核或决定。

这些是申请人提案，不是预先计算好的正面/负面 AI 结果。已实际测试 HTTP 创建、重复提交去重、修订历史以及对未经审核批准的拒绝。也检查了读取/写入分离、CSRF、格式错误输入和请求大小上限。只有完整提案 POST 接受最多 65,536 字节；现有命令端点仍为 4,096 字节。

通过项目测试工作流运行 [DeclarationTests](./dev/DeclarationTests.cls)；持久化分支需在获授权的本地会话中运行。测试涵盖不同用途、确切修订/任务/决定、篡改、目录变更、25 项历史分页以及无推理/执行副作用。所有持久化夹具均回滚。现有治理 HTTP 检查和 `Contest.RouteUITests` 仍通过。最终获授权运行通过了 86 项 D1 断言和 36 项旧 UI 断言；12 项定向 Python 测试通过。另一次权限受限 MCP 运行也通过。回读确认恰有三份声明，没有遗留持久化夹具，原有两条路由/两个批次/两次审核均未改变，且无观察器错误。

**D1 尚未实现 D2 AI 执行和 D3 浏览器表单。** 当前治理页面仍使用旧版固定路由表单；不得将其描述为已完成的新声明工作流。

## D2 implementation and acceptance status

### Runtime path

`POST /declarations/review` 接受明确的两请求同意，并原子地只预留一次确切任务。后台分发器通过 [DeclarationReviewService](./src/DeclarationReviewService.cls)，将持久化的 [DeclarationReviewRequest](./src/DeclarationReviewRequest.cls) 提交给 [DeclarationReviewProcess](./src/DeclarationReviewProcess.cls)。BP 执行 [DeclarationQueue](./src/DeclarationQueue.cls) 和 [DeclarationReview](./src/DeclarationReview.cls)；后者使用真实 `%AI.Agent` 会话进行定位和判断。HTTP 提交不会等待推理完成。

通过明确获授权的本地更新，将两个专用主机加入了正在运行的 TRIAGE Production。没有停止/重启现有 Production、IRIS 或其他主机。启动源现包含两个主机。角色、密码、命名空间映射和下游目标均未更改。

任务绑定声明/修订摘要、目录哈希、来源 Agent 修订/配置、输入哈希、提示契约和额度。记录实际互操作消息/会话 ID 和报告 ID。报告保留阶段输入、原始输出、Agent 会话 ID 和 SDK token 统计。重复同意或重复消息不能补充尝试额度，也不能重放终结任务。来源/契约变更无法消耗旧预留。重复完全相同的原始授权只会返回原任务。

### Proposal facts and sources

十一项事实包含用途、活动、预期输出、必要性、请求范围、访问、保留、共享、安排、已登记上下文和提案身份。申请人陈述仍为主张；不会伪造先前批准或投递观察。固定版本目录中的配方定义与已登记上下文一并提供，以便像 `Patient.birthDate` 这样的字段路径按拟议的仅年份转换解释，而不是自动当作完整日期。

服务器始终保留一项关于接收方/用途/数据恰当性的问题。Agent 可以指出额外的去标识化或不受支持事项，但不会因此把每个请求都变成文件清单。规范性检索复用完整来源重建/哈希验证；主要问题读取第 164.501、164.502、164.506 和 164.508 节；当声明路径确实引出去标识化问题时，可读取 164.514。引用句柄由服务器使用现有规范段落装饰器解析为确切来源段落和偏移量。来源哈希检查发现，旧基准要求其运行时文件逐字节冻结。因此保留其基础评估器/证据源不变：声明专用查找、引用物化和较大输入上限都放在新子类中实现，而不重构这些冻结文件或更改其冻结清单。

提案验证器接受基于已声明前提的推理，不会削弱发送后审核仅限观察证据的契约。服务器聚合返回 `no_risk_identified`、`risk_identified` 或 `information_required`。有依据的风险和仍待解决的重要问题可以同时存在。全无问题的结果不得隐藏重要问题。失败任务的评估/结果为空，不会捏造业务结论。

## D4 implementation and completed real acceptance

### Exact approved execution contract

[DeclarationExecution](./src/DeclarationExecution.cls) 提供逐批授权，独立于旧版全局 utilization 注册。计划要求最新的当前已提交修订、已完成的无风险任务、不可变人工批准、当前目录、有效时间范围以及受支持的四资源/七字段内部配方。计划固定提案摘要、决定/任务哈希、实际 Production 绑定/配置和由调用方指定的有界批次 ID。计划包含 `acknowledge_delivery=false`，既不推理也不投递。

明确确认会原子地只预留一次该确切批次。现有持久化 `Contest.Aggregation.Request` 和 `SendRequest` 会在 `ApprovalId`/`ScopeHash` 中携带执行授权 ID/哈希；没有更改持久消息 Storage。分发使用 UTILIZATION 中真实的 `FHIRSource → UtilizationProcess → AnalysisReceiver` BS/BP/BO。

新建的 [DeclarationBridge](./utilization/DeclarationBridge.cls) 解析声明授权，而不是创建旧注册表批准。BO 在 SQL 插入前立即重新验证确切的当前声明，并在事务完成前持有共享声明锁。并发替换、过期或已更改的批准/配置会安全失败。投影使用现有的来源推导仅年份转换，并根据获批范围检查实际叶字段。

声明批次位于 `^ContestUtilization("declarationBatch",batch)`；旧批次仍位于 `("batch",batch)`。两者共用批次/接收方锁和 SQL 主键。现有旧版观察器不会接收不兼容的批准格式。D5 必须发现声明批次并提供新的发送后适配器；D4 显示 `monitoring_state=pending_d5`。

接收方在同一事务中提交一条 SQL 行和一份收据。收据增加声明 ID/修订/摘要、确切人工决定和审核哈希、配方及执行授权。后续读取会验证收据完整性、冻结的来源/配置/输出、来源推导投影、实际范围、历史有效性、持久化请求/发送消息及其会话标头，以及当前 SQL 负载/哈希回读。结果不确定时保持 `reconciliation_required`，不创建成功收据，也不自动重放。完全相同的 POST 会返回同一执行，而不是再次发送。

## D5 automatic observed-use comparison and event handling

### Runtime wiring

[DeclarationMonitor](./src/DeclarationMonitor.cls) 是已完成声明执行的独立观察器。现有运行定时器仍会启动 `RouteReview.Pump`；该新的后台作业也会启动声明观察器。它使用单独的工作锁防止并发扫描/推理。旧路由观察器、授权和报告保持不变。D5 无需浏览器调用 `Scan`/`Pump`，也不需要新增 Production 主机、重新加载主机或重启 Production。

观察器只发现已持久化的 `delivered` 执行。旧 D4 的 `reconciliation_required` 批次不能作为成功观察到的用途处理。捕获会复用 D4 的完整来源/配置/投影/消息/会话/SQL 验证，并冻结：

- 确切的声明 ID/修订/摘要、审核任务/哈希和人工决定哈希。
- 执行授权、批次和原始收据哈希。
- 十二项有界事实：声明用途、活动、输出、访问、保留、后续共享和必要性仍为**主张**；实际限定输出和投递、项目批准及已登记合成关系是经过验证的**观察事实**；之后未观察到的行为属于覆盖边界。
- 发送后问题，用于比较实际输出/接收方和该确切获批用途，而不是通用去标识化/签名清单。

捕获的证据有独立哈希。读取和模型准入会重新验证原始收据以及底层实际批次仍匹配。报告必须匹配冻结输入、提示契约和来源 Agent；已接受结果必须匹配实际存储报告。后续编辑声明时，不会悄然用最新声明替代冻结的历史批准。

### Funding, failure and idempotence

自动发现免费执行，并创建零预算的 `blocked_budget` 记录。仅写入者可读取的计划返回绑定到已捕获证据/收据和来源 Agent 修订/配置的两请求成本计划。明确确认会存储一份不可变授权，由独立后台工作进程提取执行。浏览器永远不会调用提供方。

工作进程复用严格的 `staged-risk-v4` 两阶段 `%AI.Agent` 运行时：无工具、无隐藏迭代、每份收据最多两次请求、规范引用和经过验证观察事实的适用性/条件依据。技术故障不会替换成发现。运行中的工作进程被中断时标记为 interrupted，不会自动重试或重置额度。相同同意会返回现有记录，不会发出另一次调用。未来批次没有无限默认预算。

首次开发捕获在推理前失败，因为完整提案/收据超过现有的每条事实 2,000 字符上限。实现通过选择并拆分语义事实来修正，而非截断文本或削弱验证器。捕获失败保留在审计和 `capture_failures` 中；随后显式且免费地执行 `Recapture`，重新验证同一实际批次。只有未付费的证据失败可以使用该恢复方法；它不能重试已付费失败审核。

操作者明确允许完成 D5 真实验证所需的请求。只需且只使用了一笔有界的两请求授权；没有额外交付批次，也没有重复先前提供方运行。

### Completion and boundaries

**在有界合成应用范围内，D1-D6 已完成。** 用户创建的提案现在拥有自己的审核、修订/历史、人工批准、显式受支持执行、自动使用观察比较和事件处置。不会用原有固定路由基线替代这段完整旅程。

以下边界是有意保留的，并非隐藏的已完成功能：

- 执行仅支持已登记的内部四资源/七字段年份/就诊配方。其他声明用途/接收方可以评估，但未连接任意外部目标/投影/流水线生成。
- 实际观察覆盖配置、有界输出、消息和 SQL 持久化，不覆盖接收方未来行为、实际用途或保留/删除。模型会将这些作为覆盖边界。
- 新模型工作仍需单独的有界授权。失败/中断工作和不确定投递不会自动重放。
- 现有演示使用不同的读取者和构建者权限，但没有强制申请人和批准者身份在组织层面分离。
- 此门槛验证的是可用的本地环境和已保存演示流程。全新环境安装验收及竞赛打包/发布仍是单独任务，不属于 D6 检查器的工作。

D6 未执行竞赛发布准备、提交/推送、账户更改、Production 重启、演示重置或语料重建。
