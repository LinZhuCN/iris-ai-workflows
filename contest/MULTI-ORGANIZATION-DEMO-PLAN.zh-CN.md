## 1. Goal and scope

构建一个可复现的本地演示，从 IRIS FHIR Repository 读取合成临床数据，将其转换并分发给三个模拟组织，再使用 IRIS AI Hub 审计每个实际出站分支。UI 必须支持组织设置、执行、证据检查和人工审核，演示过程中无需终端操作。

所有系统都运行在现有 IRIS 实例中。三个接收方各有独立命名空间和应用存储。这是逻辑隔离，不是三个物理独立系统。

审计是建议性的、发送后执行的。它不会阻止投递、修改 Production 配置、授权披露或认证 HIPAA 合规。用户确认的合成档案足以作为场景前提；真实医院、合同和授权系统集成不在范围内。

## 2. Existing components and reuse boundaries

- 复用经过身份验证的工作区、API 约定和权限。
- 复用 Production 发现、明确的观察同意、不可变证据、有界 AI 审核授权、知识来源信息和人工审核模式。
- 将证据适配器扩展到现有特定 M5 请求和政策之外。不要把硬编码的 M5 政策重新标记成可配置组织档案。
- 在兼容情况下复用自有 `FHIRDEMO` 仓库基础。现有聚合工作流会写入该仓库；此新工作流从中读取。
- 保留 `PIPELINE`、`M5OBSERVATION`、现有审批和历史报告。不要替换其 Productions，也不要重新解释旧证据。
- 扩展现有 UI 表面，而不是增加另一个竞争工作区。

相关实现参考：[Production 监控](./src/ProductionMonitor.cls)、[业务证据](./src/ProductionBusinessEvidence.cls)、[审核授权](./src/ProductionReviewService.cls)、[FHIR 配置](./dev/AggregationProvision.cls)、[Production UI](../web/src/productions-page.tsx) 和[工作区导航](../web/src/app.tsx)。

## 3. Deployment and protocol boundaries

| 命名空间 | 职责 | 接口 |
|---|---|---|
| `FHIRDEMO` | 合成来源医院的 FHIR R4 仓库 | 经身份验证的 FHIR HTTP |
| `DEMODISTRIBUTION` | 新来源服务、转换 BP 和三个出站 BO | FHIR 读取；SQL、REST 和 MLLP 客户端 |
| `DEMOQUALITY` | 医院质量部门 | SQL 收据表 |
| `DEMORESEARCH` | 外部研究中心 | 经身份验证的 REST 接收方和存储 JSON |
| `DEMOCLINIC` | 外部治疗诊所 | HL7 V2 MLLP 接收方、已存消息和 ACK |
| `TRIAGE` | 组织目录、执行协调、观察和 AI 审计 | 现有受保护平台 API |

实施前，验证命名空间所有权、可用 FHIR/HL7 类、SQL 连接/驱动支持、网关路径、监听端口和许可证容量。仅配置明确归本项目所有的资源；发生冲突时失败。使用专用数据库存储接收方应用记录，不要使用共享的接收方数据全局映射。

SQL 投递必须实际连接 `DEMOQUALITY` SQL 客户端，并使用参数化语句。REST 必须发出 HTTP 请求；HL7 必须经过 MLLP 并关联 ACK。切换命名空间或直接写入全局变量都不能替代这些协议边界。

开发 MCP 调用仍固定在 `TRIAGE`。命名空间创建和本地部署遵循现有显式管理配置模式；不得绕过固定 MCP 配置，也不得通过 Web UI 暴露管理执行功能。

## 4. Organization and policy records

在 `TRIAGE` 中维护结构化、版本化记录，并通过表单录入。使用稳定的组织 ID；名称仅用于显示，不作为身份键。

1. **组织档案：**ID、名称、类型、上级组织、职责、合成场景标记、状态、修订、确认者和确认时间。
2. **主机关联：**实例、命名空间、Production、主机、Business Partner 键和组织 ID。捕获每次观察所用关联；缺失或有歧义的关联必须明确表示为缺口。
3. **接收政策：**来源组织、目标组织、用途、允许字段/类别、禁止字段、转换要求、日期精度、条件、场景依据和版本。
4. **每次运行的上下文：**所选合成队列、实际用途、导出声明、相关授权/例外事实和用户确认。

Business Partner 是原生关联，不是自由文本政策存储。机构的普遍职责不能确定每条消息的用途或许可依据。机构不同不自动意味着属于不同受保护实体；要对上级组织和场景关系建模。

草稿可编辑。已确认版本保留；编辑会创建新版本。报告保留确切档案/政策/上下文快照及哈希。配置变更不得悄然更改历史报告或活动审核范围。接收政策违规与 HIPAA 发现属于不同结果维度。

## 5. Frozen demo scenarios

提供一个来源医院档案和三个可编辑的合成目标档案预设。夹具定义输入；独立测试预期定义期望结果，绝不能将其作为答案发送给模型。

| 分支 | 用途和接收方 | 实际输出 | 验收目标 |
|---|---|---|---|
| SQL / 质量 | 同院质量统计 | 本地患者代码、出生年份和有界质量指标 | 展示已配置的最小化规则，不宣称普遍 HIPAA 合规 |
| REST / 研究 | 外部统计研究；声明 Safe Harbor 导出 | 故意保留合成姓名、MRN 和完整出生日期 | 主要矛盾：实际内容与声明及接收政策冲突 |
| HL7 / 诊所 | 对转诊合成患者进行实际治疗 | 文档化 HL7 V2 消息中的患者身份和限定转诊数据 | 展示治疗情境推理；标识符本身不构成自动违规 |

包括一个用于确定性比较的研究输出修正版。删除这些标识符不代表完全符合 Safe Harbor。不要要求模型给出全无问题的结论或压制未解决事项。不安全的合成变体必须明确标示并限制在本地自有接收方；它不是通用导出选项。

## 6. Message and evidence contracts

实现主机前先定义请求/回复契约。每次运行都有稳定 run ID；每个接收方分支都有独立 delivery ID。绑定来源 FHIR 资源 ID 和版本、来源快照摘要、档案/政策版本、转换版本、业务上下文、IRIS 会话/标头 ID 和收据 ID。

捕获实际转换后的边界：

- SQL：已执行列清单、绑定值/摘要和已提交的回读。
- REST：实际出站 JSON/摘要、HTTP 状态和匹配的已存收据。
- HL7：实际线上消息摘要、解析后的字段清单、控制 ID 和关联 ACK。传输 ACK 不能证明后续临床使用。

区分已准备、已尝试、已确认、失败和不确定的投递。保留部分成功。不得悄然重放成功分支，也不得声称网络投递恰好一次。接收方 delivery ID 用于幂等处理；结果不确定时必须对账并显式重试。

原始合成接收方数据保留在本地。模型仅接收最小化证据：字段路径、是否存在、日期精度、声明和必要上下文，而不是无界原始记录。不支持的负载和不完整捕获属于覆盖缺口，不是无风险发现。

## 7. UI deliverables

### Organizations: new workspace page

- 列出来源和目标组织及其配置的主机关联。
- 编辑档案和接收政策表单；显示草稿/已确认版本状态。
- 提供 **Fill example organizations** 和逐组织预设按钮。填充只更改表单草稿；保存/确认需显式执行。
- 替换未保存编辑前警告；重复保存不得重复建立身份。
- 在不显示实现 JSON 的情况下，让职责、可接受数据、禁止数据和条件清晰易读。

### Distribution demo: extend the existing Synthetic demo entry

- 保留现有演示，并明确标为旧版场景。
- 提供引导步骤：确认档案、准备合成 FHIR 数据、检查设置、运行一次分发、检查收据、授权 AI 审计。
- 显示 FHIR 来源和三个分支的组织、协议、命名空间、映射版本、就绪状态和逐分支进度。
- 分离 **Load synthetic FHIR data**、**Run distribution** 和 **Authorize AI audit**。填表按钮不得隐藏状态变更、业务发送或模型收费。
- 显示真实状态、错误、收据计数和部分结果。禁用重复提交，并在刷新后保留服务器执行状态。
- 不得在浏览器中提供运行时基础设施配置。

### Productions and review details: extend existing observation UI

- 显示来源/目标组织徽章和 Business Partner 映射。
- 将每个运行分支链接到实际消息证据和接收方收据。
- 突出显示 **Result / Why / Next step**。
- 比较**允许或声明的**字段和**实际发送的**字段。
- 分开显示本地政策不匹配、AI HIPAA 评估和缺失信息。
- 将完整引用、哈希、提示、用量和保留的模型输出放在可展开的审计部分。保留方便访问历史报告的能力。
- 明确显示未审核、待处理、失败和未解决状态。

所有新页面遵循现有英语 UI 约定、身份验证、授权、错误处理、响应式布局和可访问表单标签。

## 8. Implementation milestones and acceptance gates

| 里程碑 | 工作内容（含 UI） | 继续前的门槛 |
|---|---|---|
| M0：契约和就绪状态 | 验证实际 IRIS API/协议支持；冻结场景、数据契约、API 形状和页面流程 | 识别部署冲突；不替换现有 Production；不调用模型 |
| M1：组织目录 | 持久化档案、主机关联、政策、版本化确认、API 和组织表单/预设按钮 | 表单到 IRIS 往返；版本历史；预设不发送数据、不调用模型 |
| M2：三个接收方 | 自有命名空间、SQL 架构/客户端、REST 接收方、MLLP 接收方/ACK、身份验证和就绪 UI | 每种协议均实际投递并独立读回关联收据；测试负向路径 |
| M3：FHIR 分发 | 固定合成 FHIR 种子/读取、转换、BP/BO 接线、有界执行、分发 UI 和收据 | 一次运行读取 FHIR 并抵达三个接收方；验证预期负载；不调用模型 |
| M4：证据集成 | 全 Production 观察、实际分支清单、组织/版本绑定、关联证据 UI | 实际输出而非仅 FHIR 输入进入不可变证据；缺失/不匹配的绑定必须明确失败 |
| M5：AI 咨询审计 | 将现有 AI Hub 运行时适配到分支证据；有界授权；简明比较和报告 UI | 获授权的真实 AI Hub 运行、保留输出/用量、验证引用和明确的逐分支结论 |
| M6：集成验收 | 浏览器演示步骤、重启测试、回归套件和英语设置文档；更新中文演示指南 | 仅通过 UI 即可完成演示；重启后证据仍在；旧报告仍可读取 |

M1 应与其 UI 同时实现，而非将所有前端工作推迟到最后。M1 和 M2 在 M0 后进行；M3 需要两者。M4 需要目录、接收方证据和可用的分发功能。M5 需要 M4。M6 覆盖完整集成工作流。

## 9. Verification strategy

- 新 ObjectScript 行为先写回归测试；编译确切的类。使用 `%UnitTest.TestProduction`，由外部管理 Production 生命周期；测试/断言计数非零且失败为零。
- 必要时通过受控部署/测试工具，在实际专用命名空间运行聚焦测试；MCP 调用保持固定在 `TRIAGE`。
- 测试档案验证、模糊 partner 映射、过期修订、权限失败和不可变报告快照。
- 测试真实 FHIR 读取和来源版本捕获、SQL 提交/回读、REST 拒绝/超时、HL7 解析及否定/不匹配 ACK。
- 测试嵌套 JSON 和 HL7 PID 字段中的标识符、出生年份与完整日期精度差异、禁止 SQL 列、缺失来源上下文和不支持的正文。
- 验证档案字段和来源文本是不可信数据，而不是 Agent 指令。
- 验证部分投递、重复点击、显式重试、接收方去重和重启持久性，且不得重新发送已完成工作。
- 对受影响前端页面运行聚焦 Vitest 测试、TypeScript 检查、lint 和生产构建。在真实浏览器中验证引导流程。
- 将确定性证据/政策检查与模型评估分开。真实提供方调用需明确的有界授权、请求上限并保留失败尝试；常规开发期间不执行付费调用。

## 10. Final acceptance and handoff

只有在用户能够完成以下操作时，演示才算完成：

1. 在 UI 中填写、编辑并确认来源/三个接收方档案。
2. 将固定的合成 FHIR 队列加载与消息分发分开执行。
3. 运行分发并检查独立持久化的 SQL、REST 和 HL7 收据。
4. 将每个分支追踪到实际出站字段清单和组织上下文。
5. 明确授权有界的真实 AI Hub 审计并检查已保存结果。
6. 解释研究矛盾和治疗情境对照，而不把不完整检查当作法律认证。
7. 重新加载/重启后重新打开相同报告，且不重放或产生新的模型调用。

发布设置和测试命令、实施中验证的确切本地 URL 和端口、命名空间所有权、所需权限、夹具和限制。更新现有演示指南，不要将新功能描述成已可用。不得更改上游仓库或重置历史证据。
